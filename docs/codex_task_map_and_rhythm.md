# Codex Task — MAP再構築 + ランのリズム (Phase 3)

**前提: Phase 2(性能修正)が完了・受理されてから着手すること。** Phase 2の計測基準値を
壊さないことが本Taskの制約になる。

```text
Scope: MAP地形の再設計、地形タイル画像の生成、侵攻フェーズ(surge)によるランのリズム付け
Out of Scope: Element/Fusion、Equipment、Forge、HUD、職業、Damage計算式
```

**重要**: 過去の指示書(`docs/codex_task_performance.md`等)にある「Map・敵密度・Spawn率を
変更するな」という制約は、**本Taskでは解除される**。今回はまさにそこを触る。ただし
**敵の1発あたりのダメージ量は上げないこと**(理由は後述)。

---

## なぜこの2つを同時にやるのか

ヒットゲームのレビュー調査から得た結論:

- 不満で最も多いのは「一定時間以降が単調」「時間が経っても加速も激化もしない」。
- 賞賛で最も多いのは Vampire Survivors の「終盤の爆発的なパワーファンタジー」と
  Halls of Torment の「強化後も脆さが残る緊張感」。
- このジャンルの中核動詞は**カイティング(敵を引き回すこと)**。

現在のVSGameは15〜17分を「420体倒す」という単一目標で走らせており、**地形もほぼ均質な
床**のため、どこで戦っても操作の質が変わらない。地形とリズムは相互に依存する
(surgeが「どこで起きるか」に意味を持たせるには地形側の差が要る)ため、分割せず同時に扱う。

---

## Part A: 地形 — 場所によってカイティングの質を変える

> **具体的な設計は`docs/map_design_spec.md`に確定済み。** ゾーンの寸法・柱の間隔・
> 配置構造・MAPごとの構成比・生成器の自動検証項目まで指定してあるので、
> Part Aの実装はそちらを正とすること。以下は設計の意図の要約。
>
> 特に重要な前提: **1セル=32px、画面表示域は約33×19セル**。現在の
> `MIN_ROOM_SIZE 8`〜`MAX_ROOM_SIZE 14`は画面の1/4〜1/2しかなく、部屋が空間の
> 単位として認識されていない。これが「どこも同じに見える」根本原因であり、
> 部屋サイズの見直しが地形設計の前提になる。

現在の`systems/dungeon_generator.gd` / `entities/stage_environment/stage_environment.gd`が
生成する空間は、部屋と通路はあるが**戦闘上の意味の差がほぼない**。以下4種の領域を
生成に組み込み、プレイヤーが「どこで戦うか」を選ぶ意味を作る。

| 領域 | 戦闘上の意味 |
|---|---|
| **開けたアリーナ** | 大群を一掃する爽快感の場。範囲攻撃が映える。ただしsurge中は四方から来るため危険 |
| **柱林(pillar field)** | 柱を縫って敵の直線的な追跡を切る。**操作が上手いほど得をする**場所 |
| **隘路(chokepoint)** | 敵を一列に絞る。貫通・直線攻撃が強い。囲まれると逃げ場がない |
| **危険地帯(hazard)** | 通ると継続ダメージ。近道になるがリスクを取る判断が要る |

設計上の必須要件:

1. **一目で読めること。** プレイヤーが視覚だけで「ここは柱林」「ここは危険地帯」と
   判断できなければ意味がない。地形の役割と見た目を1対1で対応させる。
2. **袋小路を作らないこと。** カイティングが成立しなくなる完全な行き止まりは、
   このジャンルでは理不尽な死に直結する。生成後に到達性を検証すること。
3. **柱は`collision_layer=1`(壁と同じ)に置くこと。** 敵の`collision_mask=1`が
   そのまま効き、敵も柱を避ける。今回の性能修正で敵同士の押し合いは外したが、
   **壁への衝突は残してある**ので、柱を回り込む挙動は追加実装なしで成立するはず。
   実際にそうなるか確認すること。
4. **性能を悪化させないこと。** 柱を大量に置けば静的CollisionObjectが増える。
   Phase 2で追加した`tests/map_performance_accumulation_check.gd`で再計測し、
   **Phase 2完了時点の数値と比較**すること。悪化した場合は柱の密度を下げる。

## Part B: 侵攻フェーズ(surge) — ランに心拍を与える

15〜17分の単一目標を、**3〜4回の山**に分割する。

### 発動条件

**既存の「撃破数 or 救済タイマー」パターンを流用すること**(`map_run_controller.gd`が
Boss解放で既に使っている考え方)。新しい仕組みを発明しない。

- 撃破数が必要数の25% / 50% / 75%に達したらsurge開始。
- 一定時間到達しなければ時間側でも発動(遅いプレイヤーが山を1回も見ない事態を防ぐ)。

### surge中の挙動

- **敵の出現間隔を短縮し、同時出現数を増やす。** 密度で圧をかける。
- **敵1体あたりのダメージは上げないこと。** レビュー調査で最も嫌われていたのが
  「理由もわからない即死」「見えない敵に殺される」。密度で緊張を作り、
  一撃の理不尽さでは作らない。既存の`HealthComponent`の1発上限
  (`MAX_DAMAGE_PER_HIT_RATIO`)も維持する。
- **開始と終了が明確にわかること。** HUDに現在surge中であることを出す。
  効果音・画面の色調変化など、見逃しようのない合図を付ける。
  (HUDは`ui/hud/hud.gd`に既存の`set_room_message()`等がある。新規UIを作る前に
  既存の表示経路で足りないか検討すること。)
- **必ず終わること。** 終了時に確定報酬を出す。「耐えきった」という達成感が山の意味になる。
- **地形と噛み合わせること。** surge中は開けたアリーナが危険になり、柱林・隘路の
  価値が上がる。Part Aの地形差が、ここで初めてプレイヤーの意思決定になる。

### 数値

初期値は提案であり、実測して調整してよい。調整した場合は根拠を報告に含めること。

- surge継続時間: 40〜60秒
- surge中の出現間隔: 通常の0.5倍程度
- 同時出現数: 通常の1.5〜2倍
- **敵の同時存在上限(現在32/40/48)は超えないこと。** ここを超えると性能に直撃する。
  上限内で「間隔を詰める」ことで圧を作る。

## Part C: タイル画像 — **作成済み。生成し直さないこと**

> **タイルセットは既に完成している。** `assets/tiles/dungeon_tileset_retro.png`
> (16x16タイル / 8列×6行)。HUDと同一パレットで、4種の床・壁・柱・噴出口・瓦礫・
> 小物を含む。atlas座標の対応表は`docs/map_design_spec.md` 5節にある。
>
> 生成スクリプトは`tools/generate_dungeon_tileset.ps1`。**色や密度を調整したい場合は
> このスクリプトを直して再実行すること**(PowerShell 5.1はBOMなしUTF-8を誤読するため、
> 編集後は必ずBOM付きUTF-8で保存してから実行する)。
>
> Codexの作業は「このタイルセットをTileSetリソースへ組み込み、生成器から正しい
> atlas座標を引く」ところまで。**新しい絵を描き起こす必要はない。**
> `_preview_tileset.png`は目視確認用なのでゲームには読み込まないこと。

### 方針: 全面描き直しではなく「既存タイルの色調変換 + 新規タイルの生成」

既存の`Dungeon tileset.png`(16x16単位・24列×12行)を捨てて一から描き起こすのは
リスクが高く、品質も安定しない。以下の2段構えで進めること。

**C-1. 既存タイルをHUDのパレットへ寄せる**

先日実装したHUDのレトロ16bit調(`ui/common/retro_hud_style.gd`)に画面全体を揃える。
参照すべき色トークンは同ファイルに定義済み:

```
void       #241f45   void-deep  #150f30
parchment  #fff8e8   bronze     #e8ab1f   bronze-light #ffe27a
```

既存タイル画像を読み込み、**色をこのパレット方向へ写像した新しいPNGを出力する**
スクリプトを書く。元画像は上書きせず別ファイルとして出力し、いつでも戻せるようにすること。

**C-2. 新地形用のタイルを生成する**

Part Aで追加した領域(柱・危険地帯・アリーナ床・隘路壁)のうち、既存タイルで
表現できないものだけを新規生成する。**既存タイルで足りるものは流用すること。**

### 生成手法

このプロジェクトには**手続き的にピクセルアートPNGを生成した実績がある**
(`assets/vfx/elements/`のlight/dark/fusion用6コマシートは、PowerShell + System.Drawingで
16x16グリッドにドット単位で描画して生成した)。同じ方式を使ってよい。

Godotの`Image` APIを使ったtoolスクリプトでも構わない。**やりやすい方でよいが、
「生成スクリプトをリポジトリに残す」こと。** 手作業で1枚ずつ描いて再現できない状態に
しないこと。後から色や密度を調整できる形にしておく。

### 品質の確認

**生成しっぱなしにしないこと。** 生成したPNGを実際に目視し、
以下を満たすまで生成スクリプトのパラメータを調整すること:

- 16x16のドット絵として読めるか(ぼやけていないか、アンチエイリアスが入っていないか)
- 床の上にキャラクターとエフェクトが乗ったとき、**キャラクターが埋もれないか**
  (地形が主張しすぎるとゲームが読めなくなる。地形は背景であることを忘れない)
- 柱・危険地帯が一目で「そういう場所」と分かるか
- HUDを重ねたとき、色が喧嘩していないか

実機(Vulkan GUI)でスクリーンショットを撮って確認すること。

## 検証

1. **性能**: `tests/map_performance_accumulation_check.gd`で再計測し、
   **Phase 2完了時点の数値と比較**する。地形追加とsurgeによる悪化がないこと。
   surge中のピーク(最も敵が多い瞬間)のフレーム時間も記録すること。
2. **到達性**: 生成されたMAPに行き止まりや到達不能領域がないこと。自動検証を書くこと。
3. **surgeの発動**: 3MAP全てで、撃破数経路・時間経路の**両方**でsurgeが正しく
   発動・終了し、報酬が出ること。
4. **既存の回帰**: `--map-runtime-check`、`--map-soak-check`が引き続きPASSすること。
5. **目視**: 実機スクリーンショットで4種の地形とsurge中の画面を確認。

## 完了条件

1. 4種の地形が生成され、一目で判別でき、袋小路がない。
2. surgeが撃破数・時間の両経路で発動し、明確な開始/終了の合図と確定報酬がある。
3. 既存の`assets/tiles/dungeon_tileset_retro.png`がTileSetへ正しく組み込まれ、
   4種の床・壁・柱が生成器から正しいatlas座標で配置されている(**新規に絵を描かないこと**)。
4. 性能がPhase 2完了時点から悪化していない(実測で比較)。
5. 既存の回帰テストがPASS。
6. `game_specification.md`と`docs/codex_handoff.md`が更新されている。
7. **敵1発あたりのダメージを上げていないこと。**

**「面白くなったか」は数値では測れない。** 実装が完了したら、ユーザーが実際に
プレイして判断する。そのため**遊べる状態で止めて報告すること**。数値調整の
やりすぎで完成を遅らせるより、一度触れる形にする方を優先する。
