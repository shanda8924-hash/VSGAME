# Codex Task — VFX生成ごとのGPU読み戻しストール除去

ユーザーの実プレイで**まだ重さが残っている**。これまでの計測(Phase 1〜3)は
「時間経過によるNode蓄積」を測っており、そちらは実際に解消されている
(Phase 3で300→1500秒のp95は18.39→16.10msと悪化していない)。

**つまり原因はもう蓄積ではない。** 別軸の負荷が残っている。

```text
Scope: VFX生成経路のGPU読み戻し除去、その効果の実測
Out of Scope: Node蓄積の再調査(解決済み)、Balance数値、Gameplay仕様、地形生成、Surge
```

---

## 特定済みの原因

`effects/attack_vfx_manager.gd:370` `_get_player_visual_height()`:

```gdscript
var texture := frames.get_frame_texture(sprite.animation, sprite.frame)
var image := texture.get_image()        # ← GPU→CPU テクスチャ読み戻し
var used := image.get_used_rect()       # ← 全ピクセル走査
```

**これがVFXを1個生成するたびに、キャッシュなしで実行されている。**

`SpriteFrames`のフレームは`AtlasTexture`(`entities/sprite_sheet_builder.gd`が生成)なので、
`get_image()`は元アトラス全体の読み戻し + 切り出しImageの新規確保を伴う。
その直後に`get_used_rect()`が切り出した全ピクセルを走査する。

### なぜこれが「遊んでいると重くなる」に見えるか

呼び出し元は`play_effect()` / `_play_element_sprite()` / `play_lightning_chain()` /
`_spawn_critical_flash()`。**1ヒットごと・1属性ごとに呼ばれる。**

したがって負荷は次に比例して増える:

- 画面内の敵数(範囲攻撃が当たる数) — 進行に伴い上限32→40→48へ増える
- 有効な属性数(1→2)と属性Lv(1→3)
- Fusion成立後のsignature/echo発生
- 攻撃速度・武器数(装備とレベルで上がる)

**どれもラン後半に向かって増える。** 経過時間ではなくビルドの成長に比例するため、
Node数ベースの蓄積Harnessでは検出できない(Nodeは0.4秒で解放され、総数は横ばいのまま)。

### Codexの前回報告にすでに症状が出ている

Phase 3の報告に「**本Runの絶対p95はWindows/GPU側の一時stallで高い**」という記述がある。
**同期的なGPU読み戻しは、まさにその「GPU stall」を起こす。** 外部要因として処理せず、
自分のコードが原因である可能性を先に潰すこと。

### 同ファイル内に「正しくキャッシュしている」前例がある

`_get_element_opaque_size()`(`_element_opaque_size_cache`)と
`_get_opaque_height()`(`_opaque_height_cache`)は、同じ`get_image()`+`get_used_rect()`を
**キャッシュ済み**。スプライトシート側だけキャッシュされ、**最も呼ばれるプレイヤー身長の
取得だけが素通し**になっている。既存のキャッシュ方式に揃えればよく、新方式は不要。

---

## 修正

### 1. `_get_player_visual_height()`をキャッシュする(最優先)

この値は**VFXの表示サイズを決めるためだけ**に使われ、最終的に`clampf(..., 24.0, 56.0)`で
24〜56pxに丸められる。アニメーションのコマ単位で追従する必要はない。

- プレイヤー接続時(`_connect_player()`)に1回計算してキャッシュする。
- 無効化のタイミングは、プレイヤー再接続時と`EventBus.run_started`で十分。
- キャッシュ未設定時のフォールバック(現在の`32.0`)は維持すること。

**毎フレーム・毎スポーンで再計算しないこと。**

### 2. `entities/pickups/ground_equipment_item.gd`のアイコン読み戻し(副次)

`:45-46`で装備アイコンの`get_image()`+`get_used_rect()`をドロップ生成ごとに実行している。
`:225-228`にも同様の箇所がある。

同じ`icon_path`のテンプレートは繰り返し出るため、**`icon_path`をキーにした静的キャッシュ**に
すること。Surge中のように短時間に複数ドロップが出る場面のヒッチに効く。

こちらは1個あたり1回でありVFXほど高頻度ではないので、**優先度は2番目**。
1の効果を単独で測ってから着手すること。

## 検証(Harnessの軸を変えること)

**既存の蓄積Harnessでは検出できない。** Node数は横ばいのまま、フレーム時間だけが伸びる
性質の問題であるため、以下の観点で測ること。

### 測定シナリオ: 「後半ビルド」を最初から与える

経過時間ではなくビルド状態に比例する負荷なので、時間を進める必要はない。

1. 属性2種をLv3、Fusion成立済み、可能なら大技も取得済みの状態を最初から作る。
2. 敵を上限(48)まで出す。
3. **プレイヤーの攻撃を実際に稼働させる**(武器を無効化しないこと。ここが今までの死角)。
4. その状態を60秒維持し、`TIME_PROCESS` / 平均Frame / **p95** / VFX生成数/秒を記録する。

### 比較

**同一の敵数・同一のNode数**で、以下3条件を比較すること:

| 条件 | 期待 |
|---|---|
| 修正前・後半ビルド | 最も重い |
| 修正後・後半ビルド | 明確に軽い。**ここが主目的** |
| 修正後・序盤ビルド(属性なし) | 参考値 |

**敵数とNode数を揃えた上で差が出れば、蓄積ではなく1回あたりの処理コストが原因だったと
確定できる。** 差が出なければ仮説が外れているので、その事実を報告すること
(無理に他の修正を重ねないこと)。

### 追加で記録してほしいもの

- 1秒あたりのVFX生成数(`_play_element_sprite`の呼び出し回数)。これがフレーム時間と
  相関するかを見る。
- 可能なら`get_image()`呼び出し回数を修正前後で比較する(修正後は0に近いはず)。

## 完了条件

1. `_get_player_visual_height()`がキャッシュされ、VFX生成ごとの`get_image()`が消えている。
2. 後半ビルド・敵48体・攻撃稼働の条件で、修正前後のフレーム時間比較が数値で示されている。
3. **敵数とNode数を揃えた比較**になっている(蓄積の影響を排除できている)。
4. VFXの見た目が変わっていないこと(サイズ・スケールが従来と同じ)。実機で目視確認する。
5. 既存の回帰(`--map-runtime-check` / `--map-terrain-rhythm-check` /
   `--map-performance-check`)が引き続きPASS。
6. `--headless --editor --quit`が0エラー。
7. `docs/codex_handoff.md`を更新。仕様変更ではないため`game_specification.md`は
   更新不要(更新する場合は性能上の注意点として簡潔に)。

## 進め方の注意

- **1(プレイヤー身長キャッシュ)だけを先に入れて測ること。** 2と同時に入れると
  どちらが効いたか分からなくなる。
- **フレーム時間の異常値を「GPU側の一時stall」「Windows側のノイズ」として片付けないこと。**
  今回の原因はまさにそう見える形で現れていた。まず自分のコードを疑う。
- 期待した改善が出ない場合、**別の修正を積み増すより先に報告すること。** 仮説が外れて
  いるなら、次に測るべき軸を決め直す方が早い。
