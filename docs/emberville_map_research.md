# Embervilleから学ぶ探索MAPと、VSGAMEへの実装

調査・実装日：2026年9月14日。対象：既存の3MAP、生成ロジック、敵配置、探索進行。既存の壁・床・小物・ランドマークの作画を維持。Ponytailは使用していない。

## 結論

参考にすべき中心は「広いダンジョンに敵を散らすこと」ではなく、**道を選ぶ → 小さな遭遇を解決する → 発見や報酬を得る → 次の目的地へ向かう**というつながりだった。

VSGAMEには、役割を持つ部屋と接続関係を先に作る生成方式、少数の固定遭遇、番人の鍵によるボス解放、発見済み範囲の探索図を実装した。ただし、Embervilleのソースコードや内部数値は入手していない。以下では、公開情報で確認できた事実と、VSGAME向けの設計判断を分ける。

## 従来のVSGAMEで不足していた構造

コードを読むと、従来方式はランダムな矩形部屋を配置順に通路で結び、さらにランダムな接続を足していた。開始地点から直線距離の大きい部屋がボス部屋になり、宝箱も距離順から選ばれる。敵は安全な床から距離を空けて選ぶ有限配置だったが、部屋の目的と編成は結び付いていなかった。

このため、長い移動がそのまま探索になりやすく、分岐先で何をするのかが弱かった。さらに、通常敵の時間湧きを止めた後も、巡回精鋭には時間経過による追加出現が残っていた。ボス解放も「倒した数、または経過時間」で、探索先の発見とは別だった。

## 実装した生成手順

1. **部屋の役割と接続関係を先に決める。** 入口、初戦、分岐、番人、合流、前室、ボス、宝箱、補給、精鋭、遺構を配置する。
2. **隣り合う配置枠だけを短い通路でつなぐ。** 第三の部屋を横切る長い直線接続を避ける。途中に折れ曲がりを作る。
3. **同じ役割でも輪郭を変える。** 張り出し、十字形、角を欠いた部屋、回廊型を組み合わせ、寸法・位置の揺らぎ・反転・迂回路の再接続をseedで変える。
4. **通り道を予約する。** 部屋中央から出入口まで3タイル幅を装飾禁止にし、鍵や宝箱の周辺にも接近スペースを確保する。
5. **既存の描画・衝突を同じ地形データに接続する。** MAP2・3のランドマークは壁面に接続し、鉱山の作業員アニメーションも残す。
6. **部屋の役割に応じて敵・報酬を配置する。** 空き床への無目的な抽選ではなく、遭遇を作る。

主経路は「入口 → 初戦 → 分岐 → 合流 → 前室 → ボス」。鍵の番人は分岐から外れた経路に置き、合流点へ戻れる。別の脇道に装備、補給、精鋭を配置する。MAP2・3では寄り道を追加する。

現在の実装は**役割付きの接続テンプレートを変形する方式**。部屋数や物語構造まで毎回無制限に生成するものではない。seedによってすべてが別物になると説明しない。今後、遊びが成立することを確認できた接続テンプレートを増やすのが次の段階。

## 広さと密度の設計値

以下はEmbervilleの測定値ではなく、VSGAME用の初期値。1タイルは32ワールドpx。

|項目|MAP1|MAP2|MAP3|
|---|---:|---:|---:|
|外接グリッド|116×94|120×97|124×100|
|役割付き区画|13|15|17|
|配置敵数（ボスを除く、精鋭1体を含む）|15|16|19|
|1回の配置単位|基本1〜2体|基本1〜2体|基本1〜2体|
|配置精鋭の能力数|1|1|2|
|通路の幅|3〜4タイル|3〜4タイル|3〜4タイル|
|通常広間の外形|12〜16×11〜15|同左|同左|
|ボス室の外形|18×18|18×18|18×18|

外接グリッドには壁や空白も含むので、「歩ける広さ」と混同しない。seed=913000の例では、歩ける床は2407 / 2746 / 3225タイル。入口から鍵までの最短移動は94 / 98 / 102タイル、入口からボス室は114 / 119 / 124タイルだった。これは3×3の通行余裕を満たす地形上の最短距離であり、戦闘・寄り道・装備操作を含む所要時間ではない。

## 敵配置と交戦の流れ

- 入口、通常の分岐、補給、遺構には敵を置かず、間を作る。
- 初戦は弱い敵1体。通常の戦闘部屋は弱い敵と標準敵を基本に2体。
- 鍵の番人は固有技を持つ強敵＋弱い敵。任意の精鋭部屋には能力付きの強敵1体。
- MAP1はスライム・オーク・大剣スケルトン、MAP2はスライム・コウモリ・重装スケルトン、MAP3は溶岩スライム・ヘルバット・重装オークを使用。
- 壁越しでは反応せず、近づくか攻撃すると交戦する既存方式を継続。追跡を長く引き延ばした場合は持ち場に戻る。帰還によるHP全回復は追加していない。
- 倒した敵は補充しない。新MAPでは時間で出る巡回精鋭も停止。精鋭の能力数も待った時間で増やさない。未発見・帰還中は周期能力も停止し、遠方から突然雷や毒を発生させない。
- 番人を倒して鍵箱を開くとボス戦を開始可能にする。撃破数や放置時間だけでは解放されない。
- 宝箱の解放にはその部屋の実際の死亡通知を使う。単にノードが消えただけでは撃破扱いにしない。ボス戦開始時も未討伐の寄り道の敵を消さない。

## 探索図と目的の表示

**Mで探索図、MまたはEscで閉じる。** 開いている間は既存モーダルと同様にゲームが休止する。訪れた部屋と周辺の道だけを記録し、未発見の鍵・ボス位置は最初から表示しない。訪問済みの部屋では入口、鍵、補給、精鋭、宝箱、ボスを表示する。

HUDは「撃破○体・時間解放まで」から、現在の区画と「鍵の番人を探す／鍵箱を開く／ボス領域へ」に変更した。鍵は進行アイテムなので、50枠の装備所持品を圧迫しない。

## ゲーム性向上で次に足りないもの

優先順位は、今回の少数遭遇を面白くする影響の大きさで付けた。下記は未実装の提案であり、完了したものとして扱わない。

|優先|課題・根拠|次に具体化する内容|
|---|---|---|
|1|**敵の役割の差。** 現在も多くの敵は追跡→近接攻撃が中心。形を変えても同じ対処が続く。|近接の圧力役＋射撃役、守る敵＋援護役など、少人数で異なる位置取りを要求する2体編成。強敵の既存予兆と速い攻撃を生かす。|
|2|**装備の属性・強度と成長曲線の再設計。** 基礎攻撃を下げても装備の加算値が大きければ序盤から危険が消える。|全200装備をレア度だけでなく役割・MAP段階・上限値で整理。職業ごとの2武器案、合成コスト、失敗時の損失を一体で設計する。|
|3|**有限の敵数に合うEXP・報酬予算。** 敵を減らすと撃破による成長機会も減る。|戦闘数、初回成長までの時間、ボス前の装備水準、回復の収支を経路別に計測。数を減らしてEXPだけ機械的に倍増するのは避ける。|
|4|**寄り道の報酬の種類。** 今回は主に装備と補給で、発見の意味がまだ単調。|救出対象、鍛造素材、NPC依頼、次回の探索を変える解放。既存の動く採掘作業員を、助ける理由のある相手へ発展させる。|
|5|**帰還して成果を使う流れ。** Embervilleの探索は町や成長へ結び付くが、VSGAMEは3MAPのラン進行が中心。|帰還・保管・補給・次の目的選択を小さく成立させる。町づくり全体を一度に追加する必要はない。|
|6|**探索構造のさらなる変化。** 今回は基本の役割テンプレートを共有している。|迂回型、二つの入口がある拠点型、見えている宝箱へ回り込む型など、役割が違う接続テンプレートを増やす。片側から開く扉や隠し道は未実装。|

成長の具体例：現行データではMAP1の通常配置15体をすべて倒すと、補正なしで計19EXP。初回成長は15EXP、次は20EXP。MAP1候補ボスは24〜25EXPなので、全討伐なら累計43〜44EXPでLv3になる計算。最短経路では戦う数が少なく、結果は変わる。これはコード上の予算計算で、装備・スキル選択を含む面白さの実測ではない。

## 確認した範囲と残る限界

- 3MAP×40seed＝120地形で、全床の接続と、ランドマーク反映後の全部屋・目的地への3×3通行余裕を確認。
- 実ゲームの3MAPで敵数、時間による補充の停止、鍵箱のロック、死亡後の解放、鍵の一回取得、ボス開始、次MAPでのリセット、探索図の休止と復帰を確認。
- 実際の壁・小物・宝箱の衝突を含め、主人公相当の半径20で各部屋と目的物への接近を確認。出入口への大型装飾の配置を防止した。
- Godotの実描画で3MAPと番人の部屋、探索図を画像化。画像を貼っただけの実装ではない。
- 確認用シーン終了時の既存ObjectDB/resource解放警告は残る。探索処理中のスクリプトエラーは解消した。長時間プレイによる面白さ、全職業の難易度、すべてのseedの保証は未評価。
- 公開ダッシュボードへのデプロイは今回の作業に含めず、ローカルの記録・画像・表示項目を同期した。

## 実装の入口

- `systems/exploration_layout.gd`：役割・地形・接続・予約領域。
- `systems/wave_spawner.gd`：部屋別の有限遭遇、死亡による制圧判定。
- `systems/map_run_controller.gd`：鍵、宝箱、ボス、探索記録の連結。
- `ui/hud/exploration_map_overlay.gd`：Mキーの探索図。
- `entities/enemies/enemy_basic.gd`：過剰な追跡から持ち場へ戻る処理。
- `tests/exploration_layout_check.gd`：地形と実ゲームの確認。

出典の事実を土台にした設計であり、Embervilleのコードや非公開パラメーターをコピーしたものではない。
