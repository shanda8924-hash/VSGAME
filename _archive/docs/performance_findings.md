## 2. 修正 A: 再探索の正のフィードバック（`components/ai/chase_strategy.gd`）

### 何が起きていたか

```gdscript
if _path.is_empty() or goal != _path_target or now >= _next_path_refresh_msec:
    _path = _build_floor_path(map, start, goal)
```

前2つの条件はどちらも毎フレーム成立しうる。探索が失敗すると `_path` は空のままだし、
プレイヤーが1マス動くだけで `goal` は変わる。つまり `PATH_REFRESH_MSEC`(280) による間引きが
**一番高コストな場面でだけ効かなかった**。

さらに1フレームあたりの実行数に上限が無かったため、フレーム時間が280msを超えると
全敵の再探索期限が毎フレーム切れる状態に入り、**フレーム時間が自分自身を維持する
正のフィードバック**が成立する。これが「一度重くなると回復しない」の機構。

### 対策

1. 再探索の判断を**経過時間だけ**に一本化
2. `MAX_PATH_BUILDS_PER_FRAME` を導入（全Agent共有の static 予算、物理フレーム単位）

### 実測

壁越しに敵40体（うち32体の視界が遮られた状態）:

```
修正前: 1021.6 ms/frame (1 FPS)、60秒以上そのまま回復せず
修正後:    0.9 ms/frame
```

## 3. 修正 B: 1回あたりのコスト上限（2026-09-05）

### §2 の詰めが甘かった点

`MAX_PATH_BUILDS_PER_FRAME = 4` は**回数だけを抑えて、1回あたりのコストを抑えていなかった**。
幅優先探索は展開セル数が距離とともに増えるので、遠い敵ほど1回が高くなる。

予算を4に決めたときの実測値「1回0.73ms」は、**プレイヤーを最も遠い敵の位置へ瞬間移動させた
直後に測ったサンプル**で、敵とプレイヤーが密集して経路が極端に短かった。実距離では5倍高い。

### 対策

1. **通行可否を配列の直読みへ**（`DungeonMap.get_navigation_clearance_data()` を追加）。
   幅優先探索は1セルにつき4回この判定をするので、1回1.4µsのメソッド呼び出しが支配項だった。
   前計算済み `PackedByteArray` を1回だけ取得し、内側ループは添字参照のみにする。
   `_has_clear_floor_line()` も同じ扱いにした。
2. **`MAX_PATH_SEARCH_CELLS = 900`** を新設。上限に達した探索は経路を諦めて空を返し、
   その敵は直進する（壁には `move_and_slide()` が沿う）。
3. **`MAX_PATH_BUILDS_PER_FRAME` を 4 → 2**
4. `goal` の算出を予算分岐の内側へ移動（予算切れのフレームで計算して捨てていた）

### 実測（同一Harness・修正前後）

床かつ3x3の余裕があるマスの組をgrid距離帯ごとに選び、`_build_floor_path()` を24回ずつ計測。

| grid距離 | 修正前 1回 | 修正後 1回 | 予算込みの最悪値 |
|---:|---:|---:|---:|
| 10 | 610 µs | 177 µs | 2.44 ms → **0.35 ms** |
| 20 | 1,040 µs | 367 µs | 4.16 ms → **0.73 ms** |
| 30 | 2,142 µs | 606 µs | 8.57 ms → **1.21 ms** |
| 45 | 2,739 µs | 710 µs | 10.96 ms → **1.42 ms** |

1セルあたり 2.5〜2.7 µs → 0.5〜0.8 µs。
**経路探索がフレームに与えうる最大の負荷が 60fps 予算の 66% → 8.5% になった。**

挙動は維持。壁越し800pxへ敵30体を置いて10秒放置すると、
平均距離 800px → 243px、視界が遮られた敵 31体 → 14体。

## 3.5 【結論】実プレイの「重くなる」はエディタ起動によるものだった（2026-09-05 確定）

**単体起動では再現しない。** プレイヤーが同じように遊んで、重くならないことを確認した。

```
Godot_v4.7.1-stable_win64.exe --path "C:\Users\USER\Desktop\Claude Code\game7.30\VSGame"
```

エディタから起動したときのゲームのコマンドラインはこうなっていた。

```
--remote-debug tcp://127.0.0.1:6007 --editor-pid 13876 --wid 788758 --position "160,66" --resolution 1600x900
```

**`--wid` が付いている＝ゲームウィンドウがエディタへ埋め込まれている。**
エディタ設定は `run/window_placement/game_embed_mode = 0`（Auto）で、埋め込みが有効になる。
埋め込みウィンドウの提示はエディタ側の合成を経由するため、単体ウィンドウより大幅に遅くなりうる。

これは §4-3 で未説明だった「CPUもGPUも余っているのに待っている」という測定値と整合する。

| 項目 | 実プレイ中（エディタ起動）の実測 |
|---|---|
| ゲームのCPU | 1コアの 36〜72% |
| GPUクロック | 240〜255 MHz（RTX 4060 のブーストは 2400MHz 超） |
| ディスク読み込み | 0.00 MB/s |

**製品として出荷されるビルドにこの問題は無い。** 毎フレーム経路に `print()` / `push_warning()` は
無く（存在する3箇所はいずれもエラー処理）、ログ転送が原因でもない。

### 開発時の回避策

エディタ設定 → 実行 → ウィンドウ配置 → **Game Embed Mode を「無効」**にする
（`run/window_placement/game_embed_mode`）。ゲームは独立ウィンドウで動くようになるが、
リモートデバッガ・プロファイラ・モニターはそのまま使える。

それでも重い場合は、残りはデバッガプロトコル側のコスト。デバッガ／プロファイラのパネルを
閉じて確認する。

### §2 / §3 の修正はこの結論に影響されない

§2 の 1021 ms/frame も §3 のベンチも、**すべて単体起動で計測している**。
エディタ埋め込みとは無関係の実在の問題であり、修正はそのまま有効。

## 4. まだ確定していないもの

### 4-1. 実プレイの「常時カクカク」→ §3.5 で解決済み

エディタ埋め込みが原因と判明した。以下は判明前の記録として残す。

**合成再現は2回試して2回とも外した。** 単体起動では最初から再現しなかったので当然だった。

- Codex の Phase 1（soldier、等速300秒、470撃破）: 全区間 p95 1.893〜2.814 ms。低下せず
- 適正配置した敵30体でのフレーム時間: 修正前 1.06〜1.53 ms、修正後 0.88〜1.41 ms

§3 の修正は「多数の敵が同時に再探索を要求したときの上限」を下げたものであって、
**実症状を再現・解消したことの証明にはなっていない。**

プレイヤー本人の観察: 「敵がたくさん湧いて、かつ敵が画面外で動いているときに重くなる」。
「常時カクカク」と「時々ガクッ」が混在している感覚。

### 4-2. 周期的なスパイク

Codex の計測で 113.2 ms と 123.0 ms の単発スパイクを観測。原因未特定。

**両方とも VRAM が約10MB増えた区間で起きている**（3回の大きなVRAM増のうち2回と一致）。

| 区間 | VRAM | その区間の max |
|---|---:|---:|
| 90→120秒 | 47.1 → 56.7 MB | **113.2 ms** |
| 180→210秒 | 56.7 → 67.0 MB | **123.0 ms** |

VRAMは段階的に増えて間は平ら。難易度カーブで新しい敵種が解禁され、初回スポーン時に
`SpriteSheetBuilder.build_sprite_frames()` がメインスレッドで `load()` する形と整合する。
ただし**未検証**。

### 4-3. CPUもGPUも飽和していない

実プレイで重くなっている最中に、実行中のプロセスを外から測った値:

| 項目 | 値 |
|---|---|
| ゲームのCPU | 1コアの 36〜72%（メインスレッドが64%） |
| GPUクロック | **240〜255 MHz**（RTX 4060 のブーストは2400MHz超） |
| GPU使用率 | 24〜40% |
| ディスク読み込み | 0.00 MB/s |
| プライベートメモリ | 734 MB、8秒間で増減ゼロ |

**計算でも描画でもなく、どこかで待っている形。** これが未説明のまま最大の手がかり。

### 4-4. 敵以外のノードと draw call の増加

300秒で敵以外のノードが約150個増、draw call 81 → 215。同区間で敵は24→20体に減っている。
**300秒時点のフレーム時間は1.04msで全区間最速なので、今回の症状の原因ではない。**
12分以上のランで効いてくる可能性がある傾向として記録する。

## 6. 計測でハマった罠（同じ失敗を繰り返さないこと）

### 6-1. vsync を切らないと何も見えない

切らないと 180Hz に張り付いて 5.56 ms 固定になる。必ず両方やる。

```gdscript
DisplayServer.window_set_vsync_mode(DisplayServer.VSYNC_DISABLED)
Engine.max_fps = 0
```

### 6-2. 敵を強制配置する計測は、配置先が有効な床か検証すること

リング状に強制配置するHarnessが**敵を壁の中へ埋めてしまい**、物理のめり込み解決が
フレーム時間を支配して「距離が遠いほど重い」という誤った表を出した（610pxで15.5ms等）。
配置先を「床かつ `has_navigation_clearance()` が真のマス」に限定し、
**壁の中に入った敵の数を毎回報告する**ようにして初めて正しい値（1.4ms）が出た。

### 6-3. 短い窓の A/B は効果量よりノイズが大きい

60描画フレーム（0.05〜0.13秒）の A/B では、**baseline 自体が 1.33〜2.22 ms、幅0.89 ms
でばらついた**。一方で最大の効果量は 0.63 ms。**効果量がノイズより小さいので順位に意味が無い。**
A/B は窓を長く取り、同一時点で baseline を複数回測ってばらつきを併記すること。

### 6-4. `--editor --quit` はパースエラーを報告しない

`tests/` の8本が削除済みAPIを参照したまま3日間壊れていたが、
`--headless --path . --editor --quit` は1件もエラーを出さなかった。
**全 `.gd` を実際に `load()` して失敗0件**を確認すること（145本中8本が失敗していた）。
さらに `lab.element_combat` のような実行時解決は `load()` でも検出できず、
実際にTestを起動して初めて出る。

### 6-5. Performance monitor の値をフレーム内訳に使わない

`TIME_PROCESS` / `TIME_PHYSICS_PROCESS` は更新特性が自前の wall frame 計測とズレる。
短いA/B区間では同じ値が続く。**帰属や加算には使わず、傾向を見るだけにすること。**
