# Codex Task — 性能劣化 Phase 2(修正) (2026-08-30)

Phase 1の計測は完了・受理済み。床装備subtreeが安定区間Node増加の96.2%、cleanup probeで
p95が`14.12→9.24ms`へ回復することまで実証された。**因果が確定しているので、ここからは修正を行う。**

```text
Scope: 床装備1個あたりのコスト削減、床装備の個数上限、Fusion markの無効参照掃除、再計測
Out of Scope: Drop率・Rarity Weight・敵密度・Balance数値、Equipment UI、Forge、HUD、Map
```

**Drop率やRarity Weightは変更しないこと。** 今回は「出る量」ではなく「残り方」だけを直す。

## Step 1: コスト削減(ゲーム性への影響ゼロ・上限方針と独立に実施)

床装備1個あたり約10 Nodeのうち、**プレイヤーが一度も見ないまま常駐しているものがある**。
これらは報酬を1つも失わずに削れる。Step 2より先に、単独で効果を測れる形で入れること。

### 1-a. `LootSpawnBurst`を仕事完了後に解放する

`entities/pickups/ground_equipment_item.gd:155-173`。`one_shot = true` / `lifetime = 0.5`で
**0.5秒で放出を終えるが、その後もNodeとして永久に残る**。解放コードが存在しない。

Godot 4の`CPUParticles2D`には放出完了時の`finished`シグナルがあるので、それで`queue_free()`
させるのが最小の修正。使えない事情があれば、プロジェクト既存の
`get_tree().create_timer(...).timeout.connect(...)`方式(`effects/effect_theme_manager.gd:83`)に倣ってよい。

**これは純粋な無駄の除去であり、見た目は1ドットも変わらない。**

### 1-b. Label 2個を近接時まで生成しない

`:69-90`の`ItemLabel`と`Prompt`は**常に生成された上で`visible = false`**にされ、
`_set_nearby_visible()`(`:216-220`)でプレイヤーが近づいたときだけ表示される。

大半の床装備はプレイヤーが一度も近づかないまま放置されるため、**その2 Nodeは一度も
描画されずに常駐している**。`_on_body_entered`の初回で遅延生成する形に変えること。

`_set_nearby_visible()`が未生成のNodeを触って落ちないようガードすること
(現在は`visual.get_node("ItemLabel")`と決め打ちしている)。

### 1-c. `LootAmbientParticles`を画面外で止める

`:138-153`は`one_shot`未設定のため常時放出し続ける。画面外の装備でもCPU上で
パーティクル計算が走っている。Phase 1でCPUParticles2Dが22→163まで増えたのはこれが主。

`VisibleOnScreenNotifier2D`の`screen_entered`/`screen_exited`で`emitting`を切り替えるのが
本命。**GDScript側で毎フレーム距離計算をしないこと**(81個ぶんのスクリプト処理を毎フレーム
回すのは本末転倒)。エンジン側で判定させる。

高Rarityの追加パーティクル(`:91-106`)にも同じ扱いを適用する。

画面内に戻ったときに自然に再開するか目視確認すること。再開時に不自然な爆発的放出が
起きるようなら`emitting`ではなく別の手段(`speed_scale = 0`等)を検討してよい。

### Step 1完了時点で一度計測する

Step 2を入れる前に、**Step 1だけの効果**を同じHarnessで測ること。ここで
「1個あたりのNode数」と「CPUParticles総数」がどこまで下がったかを数値で押さえる。
この数字がStep 2の上限値を決める根拠になる。

## Step 2: レア度考慮の個数上限(ユーザー承認済みの方針)

### 設計

**2段構えにする。低Rarityだけを上限対象にし、高Rarityは自動削除しない。**

| Tier | 対象 | 挙動 |
|---|---|---|
| 低 | uncommon / rare / epic | 個数上限あり。超過時は**最も古いものから**削除 |
| 高 | legendary / mythic | **自動削除しない**。上限にカウントもしない |

理由: プレイヤーがボス戦中で拾いに行けない状況でMythicが消えるのは、性能改善で得られる
快適さに見合わない損失になる。一方でuncommon/rareは数で押し寄せる側であり、
古いものが静かに消えても実害がほぼない。高Rarityは出現頻度自体が低い(mythicのweightは1%)
ため、上限から外しても蓄積の主因にはならない。

**上限値はハードコードせず`data/equipment/drop_table.json`に置く**(例: `ground_item_low_rarity_cap`)。
初期値は**24**を提案するが、Step 1の削減結果を見て調整してよい。調整した場合は
その根拠となる実測値を報告に含めること。

### 実装場所

`systems/equipment_drop_system.gd`の`_spawn_equipment_drop()`(`:37-52`)を唯一の関門にする。
`_on_enemy_drop_requested()`(敵撃破)も`spawn_treasure_drop()`(宝箱)も**両方この関数を
通っている**ことを確認済みなので、ここ1箇所で全経路をカバーできる。個々の
`GroundEquipmentItem`側に上限判定を分散させないこと。

現存する床装備の列挙には既存のgroup `"ground_equipment"`
(`ground_equipment_item.gd:18`)を使う。生成順は`get_nodes_in_group()`の順序に依存させず、
生成時刻を各itemが自分で保持する形にすること(順序が保証されないため)。

### 消滅予告(ユーザー承認済み)

削除対象に選ばれた装備は、**即座に消さず点滅させてから消す**。

- 点滅時間は1.0〜1.5秒程度。この値もできれば上記JSONに置く。
- 点滅中にプレイヤーが拾えた場合は、**正常に取得できること**。`collect()`(`:222-231`)は
  `queue_free()`するので、**残っているTweenやTimerが解放済みNodeに触って
  エラーを出さないよう必ず停止させること**。ここが最も事故りやすい。
- 点滅待ちの装備は「削除予約済み」として扱い、**同じ装備が二重に削除対象へ
  選ばれないようにする**こと。
- 点滅中も上限カウントに含めるか外すかは実装しやすい方でよいが、
  **どちらにしたか報告に明記すること**。

点滅演出のTweenが新たな常駐コストにならないよう注意する(削除される直前の
1〜1.5秒だけ動くので問題ないはずだが、Tweenが孤児化しないことは確認すること)。

## 検証(今回は基準値があるので比較必須)

Phase 1で`tests/map_performance_accumulation_check.gd`と基準値が揃っている。
**同じHarness・同じ条件で再計測し、Phase 1の数値と並べて報告すること。**

最低限、以下が示されていること:

1. **安定区間で床装備数が上限付近で頭打ちになる**(単調増加が止まっている)。
   Phase 1の`11→81`に対する今回の値。
2. **総Nodeが安定区間で頭打ちになる**。Phase 1の`1039→1768`(+729)に対する今回の値。
3. **Frame p95が劣化しなくなっている**。Phase 1は`11.4864→13.1800ms`(+14.7%)だった。
   前半区間と後半区間の比較で、この悪化幅がどこまで縮んだか。
4. CPUParticles2D総数。Phase 1は`22→163`。
5. **Step 1のみ / Step 1+2 の切り分け**。それぞれがどれだけ寄与したかが分かる形で。
6. Fusion markが直接`queue_free`経路でも0に戻ること。

**cleanup probeとの比較も残すこと**: Phase 1では「床装備を全部消せばp95 9.24ms」という
理想値が分かっている。今回の修正後の値がこれにどれだけ近づいたかが、修正の完成度の指標になる。

### 機能面のリグレッション

性能だけ良くなって遊べなくなっては意味がない。以下を確認すること:

- 装備を拾って装備でき、ステータスに反映される(既存の`equipment_integration_check`等)。
- 点滅中の装備を拾ってもエラーが出ず、正常に取得できる。
- 高Rarity(legendary/mythic)が自動削除されない。
- MAP遷移時の既存一括cleanup(`map_run_controller.gd:322-328`)が従来通り動く。
- 宝箱からのドロップも上限の対象になっている(同じ関門を通るため自動的にそうなるはず)。
