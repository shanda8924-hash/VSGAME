# Codex Task — 成長設計 A1: 状態の可視化と条件付き強化

**先に`docs/game_design_interlock.md`を読むこと。** 本タスクはその設計のA1にあたる。
なぜこの4つをまとめて1フェーズにしているかがそちらに書いてある。

```text
Scope: XP曲線、5状態の統一と可視化、状態を参照する条件付き強化、属性強化カード
Out of Scope: 反応(A2)、進化(A3)、装備(B)、MAP(C)、新規システムの追加
```

---

## このフェーズの狙い

現状、属性は「追加ダメージ + 副作用」でしかなく、他のどのシステムとも繋がっていない。
A1では**属性が敵へ乗せる「状態」を全システムの共通の参照先に据える**。

A1完了時点で成立すべきこと:

> 火を選んだ → 敵が燃えているのが**見える** → 「燃焼中の敵に+25%」を選べる
> → **さっきの選択が今の攻撃の価値を変えている**

この「選択が後の選択の意味を変える」状態を作るのがA1の目的。カードの枚数ではない。

---

## Step 1: XP曲線の実測と調整(最初にやること)

**レベルアップが来なければ、選択肢を何枚足しても無意味。**

論理25分のRunで記録・報告すること:

- 各レベルアップの発生時刻と、そのときのMAP/経過秒
- レベル間隔の推移(序盤・中盤・終盤)
- 3MAP合計の到達レベル

**目標: ラン全体を通じて30〜45秒に1回。** 終盤で2分以上空くなら、必要XP曲線か
敵のXP付与量を調整する。**調整した場合は根拠の実測値を報告に含めること。**

Step 2以降の価値がこの結果で決まるので、**必ず先に測って報告すること。**

---

## Step 2: 5状態の統一と可視化

### 2-1. 5属性すべてが敵に「状態」を乗せるようにする

| 属性 | 状態 | 現状 | やること |
|---|---|---|---|
| 火 | 燃焼 | `_burning_targets`で実装済み | 状態として問い合わせ可能にする |
| 氷 | 凍結/鈍足 | `StatusEffectComponent`に実装済み | 同上 |
| 闇 | 呪い | `HealthComponent.apply_curse`で実装済み | 同上 |
| 雷 | **帯電** | **未実装**(連鎖はあるが敵に状態が残らない) | **新規**: 連鎖が当たった敵に一定時間残る |
| 光 | **刻印** | **未実装**(Holy Strikeのカウンタはプレイヤー側) | **新規**: 光ダメージを受けた敵に一定時間残る |

**重要**: 帯電と刻印は「状態が乗る」だけでよい。この段階では効果を持たなくてよい
(効果はStep 4の条件付き強化とA2の反応が与える)。**新しいダメージ源を作らないこと。**

状態の保持先は既存の仕組みに合わせること。`StatusEffectComponent`が既に
`_active_effects`辞書で任意の効果名と残り時間を扱えるので、**そこへ寄せるのが自然**。
`_burning_targets`(ElementCombatSystem側)と二重管理にならないよう、
**どちらに寄せたかを報告に明記すること。**

### 2-2. 状態を「問い合わせる」共通APIを1つ作る

以降の全機能(条件付き強化、反応、進化、装備接辞)がここを見る。分散させないこと。

```gdscript
# 例。名前は既存の流儀に合わせてよい
func has_element_state(enemy: Node2D, state_id: String) -> bool
func get_element_states(enemy: Node2D) -> Array[String]
```

### 2-3. 状態をプレイヤーから見えるようにする(このStepの本体)

**見えない状態を参照する選択肢は設計として成立しない。** ここが無いとA1は失敗する。

- 敵に状態が乗っていることが**一目で分かる**こと。
- 複数の状態が同時に乗り得る(最大2属性 + 反応)ので、**2つ以上でも読めること**。
- **敵のスプライトを隠さないこと。** 敵の見た目が読めなくなったら本末転倒。

実装方法は任せる。候補: 敵の足元/頭上の小アイコン、輪郭の色、小さなパーティクル。
**HUDのパレット(`ui/common/retro_hud_style.gd`)と属性色(`ElementVFXData.attack_tint`)に
揃えること。** 新しい配色を作らない。

性能に注意すること。敵は最大48体、全員に状態表示が付き得る。
**毎フレームNodeを生成・破棄する実装にしないこと。** 状態が変化した時だけ更新する。
既存の性能Harnessで悪化がないことを確認する。

## Step 3: 属性強化カード(既存値の増幅)

`element_combat.json`の値へ係数を掛けるだけで実装できるもの。**新挙動は作らない。**

**火**: 熱波(`burn.aoe_radius` +35%) / 焦熱(`burn.tick_damage_ratios` +40%) / 灰燼(`burn.duration` +50%)
**氷**: 永久凍土(`slow.duration` +60%) / 絶対零度(`freeze.chance` +15pt) / 深凍(`freeze.duration_by_stack` +50%)
**雷**: 雷速(`chain.jump_counts` +1) / 過負荷(`chain.decay_ratios`の減衰を各段+0.10緩和) / 電界(`chain.range_by_stack` +25%)
**光**: 連撃聖光(`holy_strike.trigger_counts` -1) / 裁き(`bonus_damage_ratio` +50%) / 加護(`shield_max_hp_ratio` +50%)
**闇**: 深淵(`curse.bonus_damage_taken_ratio` +12pt) / 呪縛(`curse.duration` +60%) / 侵蝕(闇の`damage_ratios` +25%)

- **所持している属性のカードだけ**を候補に出すこと。
- 同じカードは重複取得可(スタック)。ただし取得回数に応じて出現重みを下げる。
- 効果が**画面で見えること**を確認する。雷速を取ったら連鎖が実際に1本増える。

---

## Step 4: 状態を参照する条件付き強化カード(A1の核心)

**ここがA1で最も重要。** Step 2で可視化した状態を、選択肢が参照するようにする。

これにより「火を選んだこと」が「その後の全ての攻撃の価値」を変える。
選択同士が初めて噛み合う。

### カード例(各状態2枚 = 10枚)

- 燃焼: 「燃焼中の敵への与ダメージ +25%」 / 「燃焼中の敵を倒すとXPが+1」
- 凍結: 「凍結・鈍足中の敵への与ダメージ +25%」 / 「凍結中の敵への会心率 +15pt」
- 帯電: 「帯電中の敵への与ダメージ +25%」 / 「帯電中の敵に当てると連鎖が+1」
- 刻印: 「刻印中の敵への与ダメージ +25%」 / 「刻印中の敵を倒すとShieldを得る」
- 呪い: 「呪い中の敵への与ダメージ +25%」 / 「呪い中の敵を倒すと周囲の敵にも呪いが乗る」

**出現条件**: その状態を発生させる属性を所持している間だけ候補に出す。
持っていない属性の条件付き強化を出しても選べない。

**実装上の注意**: ダメージ計算へ条件分岐を差し込む場所を**1箇所に集約すること**。
各属性のroleへ個別に散らさない。A2/A3/Bも同じ場所を使う。

---

## Step 5: 選択肢プールの統合

レベルアップの3択は**単一のプール**から引く。並列の別システムにしないこと。

| 候補 | 出現条件 |
|---|---|
| 属性Lv上げ | `max_stack`未満の属性を所持している間 |
| 属性強化カード(Step 3) | その属性を所持 |
| 条件付き強化カード(Step 4) | その状態を出せる属性を所持 |
| 既存の汎用強化(`data/upgrades/`の16種) | 常時 |
| 職業強化(`class_*_lv2〜5`) | 既存条件のまま |

重みの原則: 属性Lvが上限未満の間はLv上げを優先的に見せ、上限後は強化カードが主になる。
**前半は属性が育ち、後半は属性が深まる**形にして、成長を途切れさせない。

既存の`data/upgrades/`のJSONスキーマ(`id`/`display_name`/`effect_type`/`category`/
`value`/`description`)を流用すること。**新しいスキーマを作らない。**

---

## 検証

1. **XP曲線**が目標(30〜45秒/レベル)に収まっている。修正前後の比較を出すこと。
2. **5状態すべてが敵に乗り、実機で目視できる**。2つ同時でも読める。敵が隠れていない。
   スクリーンショットで示すこと。
3. 条件付き強化の効果が**実際に条件で分岐している**こと。
   燃焼中と非燃焼中で与ダメージが変わることをログで示す。
4. 論理25分のRunで、**終盤も意味のある3枚が出続ける**。「選ぶものがない」
   「同じカードばかり」が起きない。実ログを出すこと。
5. 所持していない属性のカードが出ないこと。
6. **性能**: 状態表示を追加しても`--map-performance-check`が悪化しないこと。
   敵48体全員に状態が乗った状態でのフレーム時間を測ること。
7. 既存回帰(`--map-runtime-check` / `--map-soak-check` / `--map-terrain-rhythm-check`)がPASS。
8. `--headless --editor --quit`が0エラー。

---

## 完了条件

1. XP曲線が実測・調整され、根拠が示されている。
2. 5属性すべてが状態を敵に乗せ、**共通APIで問い合わせられる**。
3. 状態が**実機で目視できる**。
4. 属性強化カード15枚 + 条件付き強化カード10枚が、所持属性に応じて出現する。
5. ダメージ計算の条件分岐が**1箇所に集約**されている(A2/A3/Bが同じ場所を使えること)。
6. 終盤も選択肢が枯れない。
7. 性能が悪化していない。
8. `game_specification.md`と`docs/codex_handoff.md`を更新。
9. **新しい並列システムを追加していない。** 追加したのは既存システム間の参照だけ。

**A2(反応)・A3(進化)へ勝手に進まないこと。** A1を遊べる状態で止めて報告する。
面白さは数値で測れないため、ユーザーの体感評価を得てから次フェーズを決める。
